Connected Healthcare Workflow

Headless real-time synchronization service for home healthcare systems

Challenge 03 / Healthcare Integration Customer: Team Select Home Care Stack: TypeScript, Kafka, PostgreSQL

Problem

A home healthcare organization operates across 55 locations. Disconnected applications hold patient and employee information. Manual updates and daily synchronization create delays — a contact-information change in one system may not reach others, and teams act on outdated records.

Solution Architecture

A headless workflow service sits between all source systems. It consumes events in real time, validates them, resolves conflicts deterministically, persists an authoritative record, and emits updates to every connected application.

Source System → Kafka Inbound → Validate → CRDT Merge → Persist + Audit → Emit Downstream

Pipeline Stages

4. Permission Tag Attaches role-based access metadata so downstream systems enforce HIPAA field visibility —
5. Emit Publishes to Kafka outbound topics + Socket.IO for real-time UI updates Failed delivery → Dead Letter Queue with exponential retry

Key Design Decisions

Conflict Resolution: LWW Register

Each field carries its own timestamp. A single atomic SQL statement resolves conflicts — no application-level locks, no race conditions. Replaying the same event is idempotent.

INSERT INTO field_timestamps ...
ON CONFLICT DO UPDATE
WHERE updated_at < EXCLUDED.updated_at
Authoritative Record

The field_timestamps table is the source of truth — one row per field per entity, tracking when and by whom it was last written. The CRDT guarantees two systems processing the same events converge to the same state.

Audit Trail

Append-only audit_log records every field-level change attempt: who, when, from which system, old value, new value, outcome, and reason. Rejections are logged alongside successes.

HIPAA Safeguards

Events carry access control metadata. The service enforces field visibility server-side per role — Admin sees all, Nurse sees care-relevant fields, Scheduler sees logistics, Read-Only sees names. Patient diagnosis is redacted for non-admin roles.

Failure Handling

1
Bad Data  Rejected at gate
Validation catches invalid input before persistence. The field is rejected, the reason is audited, and the source system is notified. Other fields in the same event process independently.
2
Concurrent Conflict  LWW resolves
Two systems update the same field simultaneously. The CRDT merge picks the newer timestamp atomically. Both values are audited — the winner as "applied," the loser as "conflict_rejected."
3
Delivery Failure  DLQ retries
Downstream emit fails (Kafka unreachable, network issue). The event is already persisted and audited. Failed delivery goes to a Dead Letter Queue with exponential retry (30s → 60s → 120s, max 3). Exhausted items alert via Datadog.
4
AI Validation Down  Graceful pass
Notes parsing fails or times out. The update is allowed through (explicit rules are the hard gate). The audit log records the skip. No legitimate update is blocked by a secondary system's outage.
5
Service Crash  Kafka replays
Events in Kafka are retained. On restart, the consumer resumes from its last committed offset. The CRDT merge is idempotent — reprocessing produces the same result with no duplicates.

Non-Realtime Ingestion

Not all source systems can emit events. The service supports two ingestion paths:

Real-Time (Primary)

Source systems POST events via REST or produce directly to Kafka. Propagation is sub-second. This is the path used by systems with webhook or event support.

Polling Fallback

A configurable poller queries legacy systems on an interval, diffs against the last snapshot, and produces standard events to Kafka. From that point, the pipeline is identical. Latency equals the poll interval — still dramatically better than daily batch sync.
